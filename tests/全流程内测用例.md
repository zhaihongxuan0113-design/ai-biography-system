> 版本：v1.0 ｜ 更新日期：2026-09-05 ｜ 适用阶段：内部测试（MVP）

## 场景 1：建立长者档案

- **测试目的**：验证《长者档案模板》能被家人/助手顺利填写，字段足够支撑后续访谈，且老人原话能被保留。
- **前置条件**：打印版 `长者档案模板.docx` 或电子版 `docs/长者档案模板.md`；「测试长者001档案」作为参照样例。
- **操作步骤**
  1. 打开 docs/长者档案模板.md，按「测试长者001档案.md」样例了解填写口径；
  2. 陪长者（或由助手代笔）填写：基本信息、家庭信息、人生阶段、兴趣爱好、重要记忆五部分；
  3. 长者口述部分照原话记录，不改成书面语；
  4. 填写完成后保存为「长者档案_姓名.md」，先存本地，再提交到仓库 tests/（内测）或 docs/（正式）。
- **预期结果**
  - 五大部分全部有内容，关键字段（姓名、出生年月、出生地）无缺漏；
  - 口述内容保留方言、口头禅，可读性不影响理解；
  - 档案中「重要记忆」与《访谈提纲》问题能对应上（方便后续成书取素材）。
- **实际结果**：（待填）
- **通过标准**
  - [ ] 五大部分字段齐全，无空白关键项
  - [ ] 口述内容含至少 2 处口语化表达（原话保留）
  - [ ] 打印版填写的档案能无损誊回电子版

## 场景 2：发送第 1 周共 2 个访谈问题

- **测试目的**：验证定时任务能按 50 周计划，每周取 2 个未发送问题（周一、周四各 1 个），并自动建 Issue 通知。
- **前置条件**：.github/workflows/weekly-question.yml 已推送到 main；仓库成员已 Watch 本仓库并开启邮件通知。
- **操作步骤**
  1. 首次由管理员在 Actions 页面「Run workflow」手动触发一次（或 API 触发 workflow_dispatch）；
  2. 观察 Actions 运行结果与 Issue 列表：应新建 1 个带 `interview-question` 标签的 Issue，标题含「第 1 问」；
  3. 检查邮箱：应收到 GitHub 通知邮件（问题被指派给仓库所有者）；
  4. 周四等待定时任务（北京时间 09:00）自动发送第 2 问，重复步骤 2-3；
  5. 打开 Issue 核对内容：问题正文与《访谈提纲》第 1、2 问逐字一致，附追问提示与上传说明页链接。
- **预期结果**
  - 周一 1 个 Issue（第 1 问）、周四 1 个 Issue（第 2 问），标签、指派正确；
  - 每次触发都取「未发送的下一题」，不重复、不跳号；
  - 邮箱收到 GitHub 通知邮件（不产生任何费用、非垃圾短信渠道）。
- **实际结果**：（待填）
- **通过标准**
  - [ ] 手动触发后 5 分钟内新建 Issue，标签为 interview-question
  - [ ] 问题文本与《访谈提纲》对应问题逐字一致
  - [ ] 被指派账户邮箱收到 GitHub 通知邮件
  - [ ] 连续两次触发的问题序号连续（如第 1 问 → 第 2 问）

## 场景 3：模拟上传 2 段老人录音

- **测试目的**：验证录音采集规范（3-5 分钟、口语化、命名规则）与上传通道可行。
- **前置条件**：手机或录音笔；上传说明页（GitHub Pages）已可访问。
- **操作步骤**
  1. 打开上传说明页，按「第一步」检查录音环境（安静、离嘴近）；
  2. 用手机录制 2 段回答第 1、2 问的音频，每段 3-5 分钟，自然讲述（允许嗯、啊、停顿、口头禅）；
  3. 按命名规则保存：`第1周_问题1_姓名_20260905.m4a`、`第1周_问题2_姓名_20260905.m4a`；
  4. 通过说明页任一方式上传（网盘链接 / 微信发给管理员 / Issue 评论区附件）；
  5. 无真实现场录音时，使用仓库内模拟录音 tests/fixtures/ 下两个 wav 文件代替，并对照 tests/测试录音样例.md 核对内容。
- **预期结果**
  - 2 段音频时长均在 3-5 分钟，能清晰听到人声；
  - 音频内容与对应问题相关，含口语化表达、口头禅、自然停顿；
  - 上传后管理员能在 5 分钟内取得文件并播放。
- **实际结果**：（待填）
- **通过标准**
  - [ ] 2 段音频时长 3-5 分钟，文件命名符合规范
  - [ ] 音频可正常播放，音质满足转写需要（无重噪、无长时间空白）
  - [ ] 上传通道任选其一可用，且不丢失文件

## 场景 4：自动语音转文字（CrisperWhisper，逐字保留）

- **测试目的**：验证 CrisperWhisper 能逐字转写口语：保留语气词、口头禅，并标记停顿。
- **前置条件**：本地安装 Python 与 CrisperWhisper（`pip install crisper-whisper`，参考 https://github.com/nyrahealth/CrisperWhisper ）；ffmpeg 已安装。
- **操作步骤**
  1. 把场景 3 的 2 段音频放入本地工作目录；
  2. 执行转写（示例）：`crisper-whisper 录音01.wav --language zh --model base --output_format txt`；
  3. 打开生成的逐字稿，对照《语气保留指南》第一步检查：
     - 语气词（嗯、啊、那个）是否保留；
     - 停顿是否用省略号标注；
     - 情绪（笑、叹气）是否用方括号标注；
  4. 转写稿保存为「逐字稿_第1周_问题1.txt / 问题2.txt」，提交到 tests/（内测）；
  5. 无本地环境时，可用免费转写工具（如讯飞听见、微信语音转文字）代替，并人工补齐停顿/情绪标注后走同样检查。
- **预期结果**
  - 2 份逐字稿完整对应音频，无大段漏字；
  - 口语化表达、语气词、口头禅原样保留，停顿/情绪有标注；
  - 专有名词（人名、地名）出错率低（内测容忍少量错误，需人工校对）。
- **实际结果**：（待填）
- **通过标准**
  - [ ] 逐字稿与录音内容一致率 ≥ 90%（人工抽 1 分钟比对）
  - [ ] 语气词/口头禅保留 ≥ 80%（抽查 10 处）
  - [ ] 停顿与情绪标注符合《语气保留指南》约定

## 场景 5：AI 整理成传记章节（DeepSeek，保留说话风格）

- **测试目的**：验证 DeepSeek 按《语气保留指南》提示词整理逐字稿时，只做顺句分段、不改腔改词，输出可成书的章节草稿。
- **前置条件**：DeepSeek API 已配置（当前 Codex 已配置）；逐字稿已产出。
- **操作步骤**
  1. 打开《语气保留指南》第二步，复制其中的整理规则（保持第一人称、保留方言和口头禅并小注、只删重复跑题、保留情绪标注、逐句有出处）；
  2. 在 Codex 对话中粘贴逐字稿 + 上述规则，请求生成「第一章 童年记忆」草稿；
  3. 人工对照逐字稿抽查 10 句：每句都能找到出处、原词未被替换；
  4. 把草稿读给长者听，确认"这是不是您说的意思"，按反馈修改；
  5. 章节草稿保存为「传记章节_第1章_童年.md」，提交 tests/（内测）。
- **预期结果**
  - 输出为第一人称传记体，段落有序、可读；
  - 方言词/口头禅保留，必要时有小括号注释；
  - 无 AI 添加的虚构细节（人物、数字、事件均出自原稿）。
- **实际结果**：（待填）
- **通过标准**
  - [ ] 抽查 10 句全部可在逐字稿找到出处
  - [ ] 口头禅/方言保留 ≥ 80%，无删改
  - [ ] 无原稿之外的虚构细节
  - [ ] 长者回读确认通过

## 场景 6：生成带二维码的传记 PDF 章节

- **测试目的**：验证"扫码听原声"链路：原声文件 → 二维码 → 插入 PDF 章节。
- **前置条件**：场景 3 的音频已上传到可长期访问的网盘/对象存储并取得分享链接；场景 5 的章节草稿已定稿。
- **操作步骤**
  1. 把 2 段原声传到家庭网盘（如百度网盘），生成长期分享链接；
  2. 用免费二维码工具（如草料二维码 cli.im）把音频链接生成 2 张二维码图片；
  3. 在 WPS/Word 中把章节草稿排版为 A4，每章开头插入对应二维码，下方写「扫码听本章原声」；
  4. 导出 PDF：`传记_第1章_童年_测试版.pdf`；
  5. 手机扫码验证：应能直接播放对应音频。
- **预期结果**
  - PDF 正常打开，章节排版适合老人阅读（大字号）；
  - 2 张二维码分别对应 2 段正确音频，扫码即播；
  - PDF 文件大小合理（单章约 1-2MB）。
- **实际结果**：（待填）
- **通过标准**
  - [ ] PDF 可打开、字号排版无错乱
  - [ ] 二维码扫码后播放的音频与章节内容匹配
  - [ ] 单章 PDF ≤ 3MB

## 场景 7：存储成本统计

- **测试目的**：核算 2 段录音 + 文本 + PDF 的总存储空间，确认内测阶段成本。
- **前置条件**：场景 3-6 的产出文件齐全。
- **操作步骤**
  1. 查看文件属性，记录各文件大小（单位 MB/KB）；
  2. 按下表口径累加：单周存储 = 2 段录音 + 2 份逐字稿 + 1 个章节草稿 + 1 份章节 PDF；
  3. 外推 50 周总量：单周 × 50；
  4. 对照各免费额度（GitHub 仓库、家庭网盘、云对象存储）计算成本。
- **预期结果**（口径示例）
  | 项目 | 单份大小 | 单周 2 份 | 50 周 |
  | --- | --- | --- | --- |
  | 录音（mp3 128kbps，3-5 分钟） | 约 2.9-4.8 MB | 约 8 MB | 约 400 MB |
  | 逐字稿（txt） | 约 10 KB | 约 20 KB | 约 1 MB |
  | AI 章节草稿（md） | 约 15 KB | 约 15 KB | 约 0.75 MB |
  | 带二维码章节 PDF | 约 1.5 MB | 约 1.5 MB | 约 75 MB |
  | **合计** | — | **约 9.5 MB/周** | **约 475 MB** |

  - GitHub 仓库（免费）：建议只存文本/PDF/配置文件，475 MB 内 0 元；
  - 音频存家庭网盘免费档或云对象存储（如阿里云 OSS 标准存储约 0.12 元/GB/月，400MB ≈ 0.05 元/月，50 周约 0.6 元）；
  - **内测阶段总成本：0 元（免费额度内即可完成）；全部放 OSS 也仅约 0.6 元。**
- **实际结果**：（待填）
- **通过标准**
  - [ ] 单周总存储 ≤ 10 MB
  - [ ] 50 周总量 ≤ 500 MB，未超 GitHub 仓库建议值
  - [ ] 成本核算有据（记录了文件实际大小）
